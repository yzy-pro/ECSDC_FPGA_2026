# Yaw/Pitch 任意角度缓存重构方案

> 后续状态：已接入独立的 ±35° 完整帧功能路径，使用源字缓存和真实 DDR 仲裁器，见
> [大角度接入记录](20261009_pose_large_angle.md)。本文描述的高吞吐分块/多帧池方案仍是后续目标；
> 下文“现有实现”的审计针对接入前版本，新路径不实例化有缺陷的实验 allocator/scheduler。

本文件区分目标架构与现有实现。用户此前确认 1080p30、yaw/pitch 各 ±90°、
忽略 roll、视野外黑边；新增的 1080p60 需求评估见
[60 fps 预算](20261009_pose_1080p60.md)。下述完整渲染路径尚未实现。

## 现有工程的真实状态

顶层仍使用 `fram_buf_undistort` / `undistort_band_cache`，IMU 只改变各 ±2 像素
的有限平移。HDMI 光栅为 1080p60，但这不证明任意角度的位姿矫正能达到 60 fps。

新增模块的状态如下：

| 模块 | 接入状态 | 审计发现及验证限制 |
|---|---|---|
| `pose_frame_bank_allocator` | 未实例化 | 渲染中收到源帧完成会改变 `source_read_bank`；源写入没有锁定/释放协议；目标 bank 选择可能命中正在显示的帧；待发布帧也未受保护。两帧串行单测不能证明所有权安全。 |
| `pose_tile_read_scheduler` | 未实例化 | 接收口是整组 `MAX_BURST*256` bit，而 DDR 每拍返回 256 bit；14 bit 地址配 128 word 行跨度，到第 129 源行回绕；未检查 SRAM 容量；`data_last` 未校验。单测只有两行、36 beat，依赖 DUT 内部状态，没有真正注入 RVALID 间隙或校验全部地址/数据顺序。 |

这些是接口草稿，不能据其现有测试的 PASS 文本宣称完整功能通过。启用新路径前必须修正。

## 面向 60 fps 的目标数据流

```text
HDMI RGB888 -> 预处理接口 -> RGB565 -> DDR 源帧池
                                          |
绝对 yaw/pitch -> 帧姿态快照 -> 投影流水线 -> 坐标/包围盒队列
                                          |
                              DDR 请求队列 -> 源 tile SRAM
                                          |
                                 双线性采样 -> DDR 校正帧池
                                                    |
                                            VS 发布 -> HDMI
```

采集、几何计算、预取、采样/写回和显示需要重叠运行。DDR 帧池容量与片上 tile
缓存容量分别预算，不能把完整帧放入片上 RAM。

### 帧所有权

建议分别预留三块源帧和三块校正帧（逻辑帧槽，不是 DDR 芯片物理 bank）：

- 源帧在采集完成且写数据提交后才进入 ready；渲染 acquire 后保持只读锁定，直到 release。
- 校正帧区分 free、rendering、ready、displaying。显示在 VS 边界选择完整帧；释放旧帧还要
  等待旧 bank 的在途读请求排空，不能仅凭 VS 更改一个 bank 编号。
- 每帧绑定 source frame ID、姿态快照、预处理配置版本。全帧使用同一份姿态参数。
- 所有权事件必须处理同周期完成/获取/释放，以及跨时钟域确认；不能靠交替 bank 编号推断安全。
- 无空闲槽时明确记录丢帧或等待。HDMI 可重复上一完整帧维持时序，但验收 60 fps 时必须
  统计新的矫正帧，不能把重复显示算作成功处理。

三槽是吸收流水延迟/相位差的设计选择，不保证无丢帧；最终由端到端仿真和实测判定。
六槽需要扩大当前 2 bit 逻辑 bank 编号，并核对所有地址生成器及帧槽间距。

### 分块与计算

- 优先评估 64×64 输出 tile，并对源包围盒设置明确的 SRAM 容量上限；超限细分输出 tile。
  包围盒须包含全部有效四邻点，非线性畸变下只检查四角不足以证明边界。
- 计算预算倾向于 100 MHz、每拍两个输出坐标，保存首遍映射结果；几何、DMA、采样采用
  独立阶段。若先遍历求包围盒、采样时再全像素重算，即使 2 px/clock @100 MHz 也不够 60 fps。
- 坐标按 x/y 各 11 bit、小数各 5 bit、valid 1 bit 共 33 bit 估算，可按 36 bit RAM 宽度预算。
  三阶段重叠至少需考虑三份坐标槽，不能只统计 RGB565 tile。
- 四邻采样按 `(x mod 2, y mod 2)` 分 bank。每拍两个输出要求每个采样 bank 支持两次
  独立读取；下一 tile 的 DDR 填充放在不同源槽，并验证 256 bit 灌入的宽度转换和端口冲突。
- 越界、z<=0 或无效四邻点生成黑像素；黑区仍需计入输出写回和显示流量。
- 不得用源地址截断、偏移限幅或静默丢 tile 解决容量超限。

64×64 和双像素是当前预算建议，尚无新渲染器的综合资源或时序结果。近地平线的除法、
定点溢出、细分开销及无效射线判断都需独立验证。

### DDR 访问

按逐行源矩形发出对齐的 1～16 beat 请求，使用紧凑行跨度存入 SRAM。每次请求前预留
返回空间，队列记录目的 tile/偏移/长度，校验 RVALID、RLAST 和返回归属；写请求前备齐整个突发。

当前 DDR IP 不是完整标准 AXI：读通道没有 RREADY，写通道没有 WVALID，写数据由
`axi_wready` / `axi_wusero_last` 驱动。新调度器必须遵循该接口，不能假设可以暂停返回数据。
多在途请求的数量、顺序和 ID 行为需用厂商模型验证。

读写并行提交、短突发排队和合并输出写请求是 60 fps 的关键。原 `rd_ctrl` / `wr_ctrl`
彼此独立，仲裁位于 DDR IP 内部；预算工具的“每突发额外 24 拍”只是敏感性参数，不是实测延迟。

## 姿态与预处理接口

IMU 字段按有符号 Q2048 弧度角解释，使用绝对零位，忽略 roll。相机轴取 x 右、y 下、z 前：

```text
C = Ry(-yaw) * Rx(-pitch)
r_current = transpose(C) * (xn, yn, 1)
u = r_current.x / r_current.z
v = r_current.y / r_current.z
```

再应用真实标定的 fx/fy/cx/cy、k1/k2/p1/p2 得到源像素坐标。yaw 正方向绕向上轴按右手定则，
pitch 低头为正。该欧拉组合顺序需结合 IMU 固件坐标系/安装方向验证；符号约定本身不能唯一
确定两个旋转的组合顺序。参考模型的最大归一化半径限制只是防止径向多项式外推折返，
并非经测量得到的镜头视场边界。

预处理接口应放在输入 RGB888 转 RGB565 之前，保留像素、DE、SOF/EOL、frame ID、
配置版本和旁路控制；固定流水延迟必须与同步信号一起传递。物理 HDMI 输入不能背压，
预处理必须持续接收有效像素。统计结果在帧末锁存，双 LUT 在帧边界切换，统计时排除无效像素。
这只定义接入约定，不代表自动 Gamma 或直方图算法已实现。

## 既有构建能证明什么

`verification/pose_tile_interfaces_20261009/` 的 PDS 完整构建：pixel setup 0.667 ns、
DDR core setup 1.295 ns；LUT 8935、寄存器 8493、DRM18K 102.5、APM 11。
该结果对应旧有界渲染路径及默认旁路接口，未实例化的 allocator/scheduler 和关闭的处理
逻辑可能被优化掉，不能验证它们启用后的资源、时序或功能。

候选 `bitstream/EmbFPGA_1920_IMU_pose_tile_interfaces_20261009_candidate.sbit` 不含完整
任意角度 tile 渲染器，未板测。`verification/pds_20261009_164635/compile.log` 仅是随后源码
的编译检查，也不是完整渲染验证。

完成条件仍包括：安全帧池、固定点投影、容量受控的源缓存、实际 DDR 调度/写回、顶层接入，
以及带帧 ID 的连续全帧仿真、角度边界/错误注入、真实实例综合与布局布线、最终板上吞吐验证。
