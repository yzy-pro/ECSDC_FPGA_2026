# 分块 DDR 突发与延迟验证

运行命令（2026-10-10）：

```powershell
& reference/imu_cboard/.venv/Scripts/python.exe tests/run_pose_vendor_ddr.py --output verification/pose_tiled_20261010/vendor_ddr_boundary_latency
```

结果：PASS。测试连接当前 `pose_ddr_arbiter`、实际生成的 `DDR3_50H` 控制器与 PHY 仿真模型、两颗 Micron x16 DDR3 模型；源码来源和 SHA256 记录于 `source_identity.json`。

- 捕获写入与显示读回 128 个 256-bit beats。
- 渲染器测试全部合法长度 1..16；突发起点轮流落在 512/1024 个 32-bit 地址单位边界之前一个 beat。1024 地址单位为 4 KiB。
- 突发写入后逐 beat 单次读回，再执行突发读回，避免写读双方相同的回绕行为掩盖错误。
- 另外测试 16 行源图像区域，行步长 960 个地址单位，即 1920 个 RGB565 像素；用单 beat 写入建立参考，再以 9/16 beats 读回。
- 共检查 472 个写 beats、608 个读 beats（显示 128，渲染 480），检查每 beat 内容以及 LAST 位置。
- 该测试没有发现源行突发跨物理行/4 KiB 边界的功能错误。128 像素输出 tile 每行写入 8 beats，地址以 64 个单位对齐，默认 1920 行步长也整除 64，因此输出行突发不会跨 1024 单位边界。

100 MHz 用户接口上的实际模型测量：

| 事件 | 时钟数 |
|---|---:|
| AR 被接受至首个 RVALID | 27..29 |
| 8-beat 读命令至末 beat | 34..41 |
| 16-beat 读命令至末 beat | 42..49 |
| 本次 trace 的 ARREADY / AWREADY 最长等待 | 0 / 0 |
| AW 首次有效至最后一个 WREADY，最大值 | 245 |

跨行时存在额外返回空隙。因此，固定 24 周期命令延迟的行为模型不能作为真实控制器最坏延迟上界。

`sim.log` 的 Micron 命令记录显示成组刷新：第一组从 132.941725 us 开始，连续 8 次刷新，间隔 300 ns，最后一次始于 135.041725 us；第二组从 194.131725 us 开始。两组间隔 61.19 us（6119 个用户时钟），每组占用约 2.4 us。这解释了少量命令出现约 245 周期写数据停顿。并发链路的压力模型可采用每 6120 周期暂停共享 DDR 数据通道 250 周期；这是依据此 trace 的保守敏感性场景，不能代替厂商完整调度模型。

限制：测试为短命令序列，未同时施加全速捕获、渲染和显示；不能据此证明整帧 30 fps 或板级时序。日志中 33 条 Warning 来自旧版生成 IP 与仿真库端口、位宽以及 ModelSim 优化设置；没有仿真 Error、Fatal 或 Micron 时序违规。完整并发帧率、最终 PDS 时序以及上板表现需要分别验证。
